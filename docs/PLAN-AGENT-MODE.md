# agent 模式：正文是文件，对话是对话

2026-09-21 用户提出并定案为**第三种模式**，定名「agent 模式」。本文只是设计，**用户明确「暂时不推进这个计划」**——先出小版本修 1.6.x 缺陷。动手前须重读本文并再答一次铁律四三问；文中所有文件:行引用都是 2026-09-21 的快照，实施时以当时代码为准。

前身是 [小说创作模式的延期构想](PLAN-NOVEL-MODE.md)（2026-09-07：把整个上下文当稿纸、每次回复是一个章节、可回到任意章节修改）。本文把那个构想换成更硬的形状。

## 一、用户定案（原话大意，不得改写）

1. 「我自己玩了一下，发现还是不能很好地将扮演与工作分开。原因是扮演外的探讨不管怎样都还是位于上下文里面，我输入后上下文里面回答，本质上还是一问一答。」
2. 「换一个思路：分离。我与 AI 的对话并不直接进入上下文；把上下文当成一个独立的工具，AI 与我探讨后把最终正文写入这个工具。我与 AI 探讨剧情，AI 设计好后输出剧情写入工具。」
3. 「作为新模式比较好，我们目前的其实也足够优秀了。」——不替代扮演模式。
4. 「模型看见稿子确实是一个非常大的问题，我们一个主打卖点就是上下文的过滤，而这个不止没有过滤，反而引入了另一个新的上下文。」（本文第三节回答。）
5. 「最终形态不是右栏助手那样。从始至终只有一个输入框，多出另一个上下文，原上下文成为正文文件。最终形态应该类似 VSCode 加 Claude Code 插件：中间是文件内容，右栏是输入框加上下文。」
6. 「账本应该是不影响的：记账的是旁路模型，记录内容主要由正文决定。」
7. 「这个模式就叫 agent 模式。这个更新有些大，目前的几个修复先发一个小版本；把设计文档写好就行，暂时不推进。」

## 二、这是什么

梨园现在的形态里，**对话、正文、模型上下文是同一个东西**：用户说一句、模型演一拍，两者一起躺在会话树上，装配时投影成送模历史。这是聊天式 RP 继承来的形状，也是「扮演与工作分不开」的根源——只要正文就是对话流本身，任何插进对话流的话都天然是正文的一部分；工作模式再怎么用 `storyBranch` / `liyuanMode` 做投影过滤（`src/conversation-mode.ts:60`），用户面前的交互仍是同一条流里的一问一答。

agent 模式把三者拆开，形状就是 coding agent 的形状：

| | 扮演模式 | 工作模式 | **agent 模式** |
|---|---|---|---|
| 正文住哪 | 会话树上的 assistant 消息 | 同左（不动） | **子项目里的章文件**（第五节） |
| 用户是谁 | 故事里的 `{{user}}` | 维护者 | **合著者 / 导演** |
| 对话是什么 | 正文本身 | 维护请求与回执 | **讨论**——永远不是正文 |
| 模型上下文里有什么 | 全部正文投影 ＋ 数据块 | 原始工具过程回放 | **讨论 ＋ 项目状态块 ＋ 它自己读过的章** |
| 正文怎么落 | 回复结束＝定稿 | 不产正文 | **显式写入工具**（`story_append` / `story_edit`） |
| 谁触发场记 / 压缩 / 记忆 | 回复结束（`engine.ts:1148` 起） | 不触发 | **章写入**（同一条旁路链，换挂点） |
| 预设 | 装载并转译 | 不装载 | **不装载**（第九节待定项 1） |
| 上下文过滤 | harness 确定性剔除过程数据 | — | **正文默认不在上下文里**——过滤走到极端 |

README 那张类比表（代码 ↔ 剧情正文、Edit ↔ 局部改稿、Rewind ↔ 上一拍修订）在扮演模式里是类比；在 agent 模式里是字面意思。2026-09-05 的调研结论「pi 的 8 个工具全部指向同一个名词＝工作目录里的文件；梨园的 22 个工具没有一个指向正文」（记忆 liyuan-pi-extension-survey）在这个模式里第一次被回答。

## 三、回答用户的第 4 条顾虑：模型怎么看见稿子

这不是过滤卖点的反面，是它走到极端。

扮演模式里过滤要解决的是：正文和过程数据挤在同一条流里，harness 得确定性地把工具调用、思考、状态栏从送模历史里剔出去。agent 模式里这个问题在结构上不存在——**稿子默认根本不在上下文里**，上下文只有讨论和模型自己读进来的片段。「多出一个上下文」不成立：总量没变，组成从「全部正文 ＋ 讨论」变成「讨论 ＋ 正文的必要部分」。

真正的问题只剩「读多少才够续写」，而这正是 coding agent 的老问题，答案也是现成的：Claude Code 不装整个仓库，它读打开的文件，其余靠 grep。对应到稿子：

- **前情提要**当摘要——已有（`src/stage/compact.ts:164 runCompaction` 产出的 `rp-summary`）。
- **稿子的尾部**当「打开的文件」——项目状态块里带最近若干字（第五节 5.4，一个数字参数）。
- **其余任何位置**靠读取工具（`story_read` / `story_grep`），读不读、读哪里归模型。

还有一个反向的好处：扮演模式不敢放开压缩，因为压缩丢的就是正文本身；agent 模式里真相在文件里，**讨论层可以像 pi 会话一样随意压缩**，丢了也无所谓。这是 coding agent 能压缩的根本原因，梨园第一次能享受到。

## 四、铁律四三问

**问 1 全集**：任何卡、任何长度的作品、任何模型；用户在此模式下的**一切输入都是讨论**——不存在「这句是剧情还是讨论」的分类问题，因为剧情只从写入工具进来。全集里没有「未见过的输入形状」。

**问 2 负责人**：这是一个新机制，不是补丁。负责人有三个，全是既有物或既有物的直接延伸：

- **稿子**（章文件 ＋ 会话树条目）——新建，但形状照抄上一拍修订已经落地的「稿件文件 ＋ 树条目指向 ＋ 写时复制」（[PI-RETURN-PREVIOUS-DRAFT.md](PI-RETURN-PREVIOUS-DRAFT.md) 落点与所有权一节，`src/stage/draft-projection.ts:58 applyDraftRevisions`、`src/stage/previous-draft.ts PreviousDraftEditor`）。
- **agent 轮**——`engine.ts #turn` 里 `authoringTurn` 那条路已经是「cwd＝卡目录、原始过程回放、沙箱内文件工具」的 pi 会话（`engine.ts:1258-1264`：system prompt / 工具清单 / `authoringHistory` 三处按模式分流）。agent 轮＝这条路 ＋ 稿子工具 ＋ 项目状态块。
- **旁路链**——`engine.ts:1148-1241`（场记 `runScribeTurn` → 世界线钉档 `storeSave` → 压缩 `#compact`）整段照用，触发信号从「本拍有正文」换成「本轮写入了章」。

**问 3 没见过的卡**：卡在此模式里是**素材**：`AGENTS.md`、世界书、名录、记忆按现有通道进来；卡的聊天形状资产（`first_mes`、示例对话、状态栏前端、作者正则、内嵌脚本）在此模式里不是协议——harness 只认自己发行的稿子协议（章边界、版本、引用）。任何卡行为一致；卡带的状态栏模板在稿子视图里不渲染（第七节代价 3），是预期行为不是污染。

## 五、形状

### 5.1 模式的位置：子项目属性，不是拍间开关

- `mode: "agent"` 落在子项目元数据 `对话.json`（`src/paths.ts:133 CHAT_META_FILE`）。新建对话时选「扮演 / agent」；一个子项目一种形态，**不在拍与拍之间切换**——扮演的正文在树上、agent 的正文在文件里，两者之间是转换不是切换（转换见第九节待定项 5）。
- 顶栏「扮演｜工作」两段开关（`web/src/App.tsx:1998`）在 agent 子项目里不出现：agent 模式本身就是带全部工具的工作形态，没有第二个身份可切。
- `hello` 帧的 `conversationMode`（`server/wire.ts:222`、`server/main.ts:857`）扩为三值 `"roleplay" | "authoring" | "agent"`；`src/conversation-mode.ts:2 ConversationMode` 同步。`liyuan-mode` 树条目照旧记模式与来源。

### 5.2 磁盘形状：章文件 ＋ 树条目

```
cards/<卡>/对话/<子项目>/
  对话.json            ← mode: "agent"
  会话/                ← pi sessionDir：讨论历史 ＋ 章条目 ＋ 旁路条目（rp-state / rp-summary / liyuan-sandbox …）
  正文/                ← 新：章文件，一章一文件，写时复制
    <chapterId>.md
  世界状态.json  世界线.json  面板.json  向量记忆/  稿件/   ← 现有，全部不动
```

- **章＝一次写入**。`story_append` 成功即在会话树追加 `rp-chapter` 条目 `{ chapterId, file, version, title?, chars }`；条目挂在当前叶上。**当前分支上的 `rp-chapter` 条目按序拼起来就是这份稿子**——不存在一份「总文件」，稿子是分支的投影，和今天正文是 `storyBranch` 的投影同构。
- **改章＝写时复制**。`story_edit` 不覆盖原文件：写新文件、追加 `rp-chapter-revision` 条目把同一个 `chapterId` 指向新文件与新版本；兄弟世界线看到的仍是旧版。这是上一拍修订已经验证的形状，只是从「只许改上一拍」放宽到「当前分支任意章」。
- **世界线＝树分支，章＝树节点**。`worldline_store` / `worldline_list`、回退、变体导航全部复用：回退到某章＝树导航到该节点，稿子视图随之截断；从中间某章分叉＝在该节点下写新章。`世界线.json` 不改格式。
- **章文件对原生 `write` / `edit` 只读**。沙箱判定（`src/sandbox.ts sandboxVerdict`，纯函数）加一条路径规则：`正文/` 与 `会话/` 属 harness 管理的数据目录，原生写工具拒绝，回执指向 `story_*`。这是数据规则（路径），不是识别器。原生 `read` / `grep` 照常可读——但读到的是文件不是分支投影，回执里注明「分支视图请用 story_read」这一点由工具描述承担，不加提示词。
- 章文件用 `.md`：人可读可备份；版本与归属在树上，文件不带 frontmatter。

### 5.3 工具集（梨园发行的闭合协议）

新增五个，全部落在 `src/stage/` 下一个新模块（对应 `previous-draft.ts` 的形状），通过现有 `StageTool` 注册：

| 工具 | 作用 | 契约要点 |
|---|---|---|
| `story_outline` | 当前分支的章目录：序号、chapterId、标题、字数、版本 | 无参数；是模型定位的入口 |
| `story_read` | 读章：按 chapterId 列表，或按「最后 N 字」 | 返回带 chapterId＋version 的原文；支持 UTF-16 范围（沿用 `previous_draft_read`） |
| `story_grep` | 在当前分支全部章里搜原文 | 返回 chapterId ＋ 命中行；不做语义检索（语义走既有 `memory_search`） |
| `story_append` | 追加一章 | 唯一的「定稿」入口；成功＝一次章写入，触发 5.5 的旁路链 |
| `story_edit` | 改任意章 | 沿用 `previous_draft_edit` 的全部约束：读取版本必须匹配、原文引用唯一且不重叠、整批原子、不允许清空；**不触发旁路链**（第七节代价 4） |

保留的既有工具：世界书族、向量库族、`world_state_get`、`worldline_*`、`panel_*`、`ask`、`skill_read`、媒体、MCP、`card_read` / `card_update` / `card_project`、沙箱内原生七工具（`src/sandbox.ts:21 NATIVE_TOOL_ACCESS`）。也就是说 **agent 模式的工具清单＝工作模式清单 ∪ 扮演模式数据工具 ∪ `story_*`**——它是「什么都能干的那个 agent」，只是写正文有唯一出口。

不提供的：`previous_draft_*`（被 `story_edit` 覆盖）、稿纸工具 `draft_*`（本拍草稿的概念在此模式里不存在，讨论就是草稿）、`conversation_mode`（5.1）。

### 5.4 上下文装配：四条通道，闭合

agent 轮的送模内容只有这四样，**在此声明为闭合集合**，实施时不得新增：

1. **system**：`assets/AGENT.md`（新，模式身份与稿子是什么；写法遵守既有纪律「提示词不是工具手册」——说边界、不说流程、不催告）＋ 卡 `AGENTS.md`（`materials.cardAgents`，素材）＋ 用户规则（`materials.userRules`）。`SYSTEM.md` / `APPEND_SYSTEM.md` 是扮演引擎协议，不进。
2. **项目状态块**：与扮演模式同一份数据的同一种装配（`buildStageSystemPrompt` 已有的【世界状态】【登场名录】【前情提要】【常驻摘要】，预算沿用 `src/card-memory.ts:50-52` 的 1200 / 4300 字），**多带一项「稿子尾部」**：当前分支最后 `agentStoryTailChars` 字的原文（配置项，默认值待实测，起点建议 6000 字≈最近一两章），带 chapterId 与 version，形状和 `story_read` 的回执一致——它就是「打开的文件」。
3. **讨论历史**：pi 原生消息（user / assistant / toolCall / toolResult），走 `authoringHistory` 那条回放路（`engine.ts:1264`），不走 `storyBranch` 清洗——讨论里没有正文，无需清洗。
4. **工具回执**：本轮内 pi 自持。

两种压缩，各归各：**剧情向压缩**仍由 `runCompaction` 产出 `rp-summary`，输入从「拍」换成「章」（`planCompaction` 的 beat 边界改认 `rp-chapter` 条目，`compactEveryNTurns` 语义变为「每 N 章」）；**讨论压缩**用 pi 原生的会话压缩，因为讨论不是真相——这是第九节待定项 7，首刀可以先不压。

### 5.5 定稿边界与旁路链

`story_append` 成功后，在 `#turn` 收尾处（今天 `engine.ts:1148` 之后那段）按原顺序跑：

1. **场记** `runScribeTurn`（`src/stage/scribe-run.ts`）：`assistantText`＝本章原文，`state`＝当前账本；`userText` 传空——场记读的是「已写出的正文＋当前账本」，用户输入在扮演里只是参考（实施时核对 `runScribeTurn` 对 `userText` 的实际依赖，若有则传本轮讨论的最后一条用户消息）。叶守卫、MVU 懒建、面板数据并账全部照旧。
2. **世界线钉档** `storeSave`：模型本轮调过 `worldline_store` 才有值；排在场记之后的理由不变（`engine.ts:1215` 注释）。
3. **剧情向压缩** `#compact`：按章计数。
4. **卡级记忆**：`syncCardMemory`（`src/card-memory.ts:458`）的触发单位是「一局＝一个子项目」，拍外完成——不变。局复盘的证据收集 `collectChatEvidence` 从分支取正文，改认 `rp-chapter` 条目。

**一轮讨论可以写多章**（模型连续两次 `story_append`），每次各触发一遍；也可以一章不写（纯讨论），什么都不触发。**`story_edit` 不触发任何旁路**——改中间章后账本、摘要、后续章的协调照旧留白（与上一拍修订同一条留白，见 [PLAN-NOVEL-MODE.md](PLAN-NOVEL-MODE.md) 与 PI-RETURN-PREVIOUS-DRAFT.md「工具与边界」末条）。真要跟改，由模型自己决定「我改了这里，后面哪些要跟」并用 `story_edit` 跟——像改函数签名后 grep 调用方，harness 不猜。

### 5.6 前端：中间是稿子，右栏是讨论

- **桌面**：复用 `center-studio-split` 4:6 外壳（`web/src/app.css:8144-8172`），比例反过来：**稿子视图 60%，讨论 40%**。稿子视图＝当前分支章目录 ＋ 正文连续阅读（章标题、版本角标、字数），章级「编辑」入口；讨论区＝现有消息列表 ＋ 现有输入框，只是窄了。**只有一个输入框**。工作模式的写卡平台（`CardStudio`，`App.tsx:2577`）在 agent 子项目里仍可从卡详情打开，占用同一块中间区域（标签页切换：稿子 / 卡），不并排三栏。
- **手机**：稿子与讨论是两个页签，切换而不叠放；复用 `studio-split-pane` 在 `max-width: 999px` 下的全覆盖形状（`app.css:8185`）。悬浮球及其菜单（状态栏、名录、世界线）不变。
- **流式**：首刀接受「章写完整后一次出现在稿子视图」——工具参数在 pi 里是整体到达的；把 `story_append` 的正文按流式落中间栏是后续（第九节待定项 6）。讨论区的流式沿用今天工作模式的 Markdown 文本路径。
- **用户直接改稿**：稿子视图里按章编辑，提交走**服务端同一条 `story_edit` 路径**、来源标 `user`（对应今天「用户手改回复」在 `applyDraftRevisions` 里的兼容位）；不允许绕过树条目直接改文件。这一项是否进首刀见第九节待定项 4。
- 消息列表里**不再有剧情气泡**：讨论区只显示讨论；`story_append` 在讨论区显示为一张「已写入第 N 章（字数）」的内联卡片，点击定位到中间栏。不用弹窗（既有前端观感规则）。

## 六、铁律自检

- **铁律一**：不往任何既有送模文案加一句。`assets/AGENT.md` 是新模式自己的身份底座（与 `AUTHORING.md` 同级），不是补丁；它的写法受「不是工具手册」纪律约束，长度目标与 `AUTHORING.md` 同量级。稿子尾部是数据不是指令。**不加「写之前先读尾部」之类催告**——读不读归模型；连续性断了就调 `agentStoryTailChars` 这个数字。
- **铁律二**：agent 轮的通道集合在 5.4 一次性声明闭合（四条），其中三条是既有通道原样复用，「稿子尾部」并进既有项目状态块而不是另起一处。实施中任何「在 X 时机再塞一段」的念头＝违律。
- **铁律三**：稿子协议（章条目、版本、引用）是梨园自己发行的；沙箱新规则是路径数据；不做输入分类（用户输入全是讨论）、不做「这段像不像正文」的识别、不从讨论里猜剧情事实。
- **铁律四**：本文第四节；实施前重答一次。

## 七、已知代价（认下，不当 bug 查）

1. **每章至少多一轮讨论**。想快速你来我往的人用扮演模式——这正是它作为第三种模式而非替代的理由。
2. **用户不是 `{{user}}`**。沉浸感换成了掌控感；用户自己的角色也由讨论进入稿子。
3. **卡的聊天形状资产在此模式里无用**：`first_mes` 与备选开场白可作为「第一章的素材」由模型引用，状态栏前端不渲染，作者正则不跑，预设不装（待定）。这些卡在 agent 模式里「少了东西」是预期。
4. **改中间章后账本、摘要、后续章过期**，与上一拍修订同一条留白，agent 模式不让它变差，但因为改前文变便宜了会更常撞到。
5. **模型不读尾部就写会断线**。唯一的保障是尾部字数参数与前情提要，不加催告、不加检查器；断线是可见的、可由用户在讨论里纠正的失败。
6. **每章的旁路调用照旧**（场记一次，压缩到期一次），不比扮演多。

## 八、不做什么

- 不做输入分类器、意图路由、关键词触发。
- 不复活右栏助手；不做第二个输入框；不做三栏。
- 不自动重算账本 / 摘要 / 记忆；不做第二模型审稿、字数或文风检查、逐章强制计划。
- 不在扮演子项目里做拍间切换到 agent；转换是显式导出（待定项 5）。
- 不动 vendored pi；不另造循环——agent 轮走今天 `authoringTurn` 同一条 `AgentSession` 路。
- 不给章文件加 frontmatter 或第二套版本系统；版本只在树上。
- 不让原生 `write` / `edit` 碰 `正文/`。

## 九、留白与待用户定

1. **预设是否装载**。建议**不**：预设是聊天形状的引擎，规定「怎么输出一拍」；agent 模式没有「一拍」。用户 9/15 定过「采样是预设自己的域」，但那是扮演模式内的事。若用户要保留破限类块，形状应是「用户把它写进卡 `AGENTS.md` 或用户规则」，不是装载器。
2. **`agentStoryTailChars` 默认值**：实弹定，起点 6000。
3. **`story_read` 的粒度**：按章还是允许任意字符范围——建议两者都给（沿用 `previous_draft_read` 的 UTF-16 范围）。
4. **用户直接改稿是否进首刀**。建议进第三刀（第十节）。
5. **从扮演子项目导出成 agent 子项目**：用 `storyBranch` 投影把当前分支正文按拍切成章、复制账本与世界线、新建 `mode: "agent"` 子项目。一次性、单向、显式。用户提过「随意切换」的想法但最终形态定为分栏；这项作为可选后续，不进首刀。
6. **`story_append` 正文流式落中间栏**：需要工具参数的增量事件，pi 是否暴露待查；首刀不做。
7. **讨论层压缩**：pi 原生会话压缩 vs 自管。首刀不压，观察讨论历史实际增长再定。
8. **卡状态栏前端在稿子视图里的呈现**：不渲染是首刀定案；将来若要，形状是「面板数据→模板」（`panel_*` 那条已有的两层路），不是把消息级状态栏搬过来。
9. **多章一轮时前端的呈现顺序**、`ask` 在讨论区的形态——按实际体验定。
