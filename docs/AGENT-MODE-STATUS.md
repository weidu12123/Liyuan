## 二、怎么进去

形态是子项目属性，写在 `对话.json` 的 `mode:"agent"`（`ChatMeta.mode`，`createChat` / `newChatSessionDir`）。只能在**新建项目**时选定。

- 入口两处，都叫「新建项目」：左栏顶部，或顶栏「新建」菜单。弹窗里名字下面有「扮演 / agent」两张选项卡（`NewProjectBox`）。
- 「新建对话」不是入口。它在当前项目里再开一个会话，不问形态。
- 建好之后不能切换。`setMode` 拒绝进出 agent。扮演项目顶栏仍是「扮演｜工作」；agent 项目没有这段开关，换成 `agent · 稿子 N 章`（手机上兼作稿子页签）。
- 扮演子项目导出成 agent 子项目：设计里标为可选，没做。

## 三、上下文里有什么

扮演模式下，对话、正文、送模历史是同一个东西。agent 模式把三者拆开：正文是产物，对话是讨论，讨论永远不进正文。

agent 轮复用 `authoringTurn` 那条 pi 路（原始过程回放、沙箱、原生工具），但 system 不是扮演那一份，也不是工作模式的 `AUTHORING.md`。`engine.ts` 里 `authoringTurn` 为真时，送出去的 system 是 `workPrompt`；agent 轮的 `workPrompt` 来自 `agentSystemPrompt`。

agent 的 system 只有这些：

- `assets/AGENT.md`（模式身份；说边界，不说流程，不催「先读尾部」）
- 用户规矩：全局与卡级 `APPEND_SYSTEM.md`，和扮演读的是同一对文件
- 卡 `AGENTS.md`（`{{char}}` / `{{user}}` 宏照常求值）
- 两行事实：工作目录、当前角色卡路径

不装的：预设、`SYSTEM.md` 那套扮演协议、角色描述/性格/场景/对白示例的兜底段、「用户扮演：名字」段、常驻世界书、每拍注入。

送模内容在设计 §5.4 声明为闭合的四条，实施没有加第五条：

1. 上面这份 system。
2. 项目状态块，由 `prependToLastUser` 压在本轮用户原话前，**不落树**。顺序：前情提要（含常驻摘要）→ 世界状态 → 登场名录 → 稿子尾部。尾部默认最后 6000 字（`agentStoryTailChars`），从末章往前取，装不下的章在预算内找段落边界，否则硬截。
3. 讨论历史：`authoringHistory` 回放。
4. 本轮工具回执。

稿子默认不在上下文里。尾部是唯一主动带上的原文；其余位置读不读归模型。

## 四、磁盘：不是一章一个文件

`paths.ts` 的注释写着「一章一文件，写时复制」。目录确实有，但**打开目录看不到这份稿子**。

```
cards/<卡>/对话/<子项目>/
  对话.json                 mode: "agent"
  会话/                     pi sessionDir：讨论、章条目、修订条目、rp-state、rp-summary
  正文/
    <chapterId>.v1.md
    <chapterId>.v2.md
  世界状态.json  世界线.json  面板.json  向量记忆/  稿件/
```

- 章 id 是 `YYYYMMDD-HHMMSS` 加 2 字节十六进制（`newChapterId`），不是「第1章」，也不是稳定路径。
- 文件名是 `<chapterId>.v<n>.md`（`chapterFileName`）。`StoryStore.write` 见到同名文件就抛，绝不覆盖。
- 一次 `story_append` 写 `v1` 并在树上追加 `rp-chapter`。一次修订再写 `v<n+1>` 并追加 `rp-chapter-revision`。旧文件留着。
- **当前稿子＝当前分支上这些条目的投影**（`projectChapters`）。顺序、标题、哪一版算当前，都在树上，文件不带 frontmatter。
- 同一个 `正文/` 里同时躺着：旧版本、被回退的章、兄弟世界线的章。目录是只追加的版本堆，不是项目的文件树。

原生工具碰不到这份稿子。`harnessManagedPath`：`对话/<id>/正文` 与 `对话/<id>/会话` 对原生 `write` / `edit` 直接 `deny`，回执指向 `story_*`；`read` / `grep` / `find` / `ls` 放行。`世界状态.json`、`创作/` 不在这条规则里。

这是扮演模式「上一拍修订」的形状（写时复制＋树条目指向），不是 coding agent 的形状（目录即项目，一个文档一条稳定路径）。

## 五、工具与编辑

五个工具，`src/stage/story.ts`，闭合协议：

| 工具 | 作用 | 不做的事 |
|---|---|---|
| `story_outline` | 当前分支的章目录：序号、id、标题、字数、版本 | |
| `story_read` | 按 chapterId 列表读，或 `tail` 最后 N 字；单章可给 UTF-16 的 `start`/`end` | |
| `story_grep` | 当前分支全部章里搜原文，返回章号与命中行 | 不做语义检索 |
| `story_append` | 追加一章。唯一的定稿入口 | |
| `story_edit` | 改当前分支任意一章 | 不触发场记、记账、压缩 |

何时写、何时改，harness 不决定。一轮讨论可以一章不写，也可以连写几章。没有「该写了」的催告。

`story_edit` 的约束沿用 `applyDraftEdits`（`src/draft.ts`）：

- 必须带上读到的 `version`，不一致则整批不改。
- 每一处是 `old`/`new`。`old` 必须在该章里逐字出现且只出现一次；多次出现就拒绝，回执要求前后再带一句使其唯一。
- 一章内多处修改整批原子：任一处定位失败、引用重叠，全部不改。
- 不许清空整章。
- 寻址是「引用唯一原文」，不是「第几句」。

分类单位是章，不是消息，也不是每次编辑。一章＝一次 `story_append`。`story_edit` 不产生新章，只把版本加一，来源标 `agent`。

用户在稿子视图里按章「编辑」走 `POST /api/story/edit` → `replaceChapterText`：同一条修订落点，来源 `user`，但是**整章替换**。原文没变不落新版本。

跨章修改今天做得到，但是 N 次调用：`story_grep` 找出命中，再对每一章各调一次 `story_edit`。没有「这一批要么全成、要么全不改」，没有一份可以整体看、整体撤的变更集。同一句式在一章里出现多次时，唯一性约束和这个用法是对着干的。要改哪些句子归模型，harness 不维护句式名单。

## 六、历史与回退：会话树，不是 git

本地历史是 pi 的会话树。条目只追加。回退是 `navigateTree` 把叶子挪走；被退掉的内容还在树上，可以再导航回去，从那里继续写就是分叉。章文件因为写时复制，旧版本还在磁盘上。没有 git 仓库，不能把某一章的某一版单独检出盖回当前分支。

两种回退，粒度都比「某一次输入」粗或偏：

- `/rewind N`（`.liyuan/extensions/roleplay.ts`）：agent 子项目按**讨论轮**数，数的是原始分支上的用户消息，不是 `storyBranch`。退 N 轮会把那几轮讨论和其间写入的章一起退出当前分支。停在那条用户消息之前。入口是自己数轮数敲命令，没有可点的输入清单。
- 稿子视图「回退到此章之后」：`chapterRewindTarget` 停在写出该章那**一整轮**的末条（收尾的 assistant 之后还有场记的 `rp-state`）。同一轮写了多章时，退到其中任一章都保留整轮，退不掉这轮中间的某条消息。

`/reroll` 与 `/drop` 仍走 `storyBranch`。agent 的讨论消息被 `storyBranch` 滤掉（`messageMode === "agent"` 不进 story 流），这两个命令在 agent 子项目里找不到用户轮。

会话树记住修订，也提供「退到某个节点」。它执行不了跨章修改，也聚合不了一次改动碰过的多个文件。

## 七、旁路

只挂在 `story_append` 成功之后（`#afterChapters`），一章一遍，顺序与扮演相同：

1. 场记 `#scribe`。`userText` 传空；`buildScribeTurnPrompt` 在用户原文为空时不写空的「用户：」行。
2. `storeSave`。模型这轮调过 `worldline_store` 才有值。
3. 按章压缩。实施时的取舍：keep 1 章、每章判一次、字数地板 2000 不变；`compactEveryNTurns<=0` 仍关闭。设计里的「每 N 章」没用——上下文里本来只有稿子尾部。
4. 向量记忆在宿主 `onTurnEnd` 逐章入库。卡级记忆的 `collectChatEvidence` 认章，拍数＝章数。

`story_edit` 和用户整章替换都不触发旁路。改中间章之后，账本、摘要、后续章过期。文风替换不该重记账；改了情节要不要跟改后面的章，留白给模型。

另一处取舍：agent 的 `ask` 是 `AGENT_ASK_TOOL` 一句话，不带扮演版那段触发规则。同名工具以它为准。

工具清单＝扮演的数据工具 ∪ `skill_read` ∪ 这个 `ask` ∪ 媒体 ∪ MCP ∪ 工作模式的写卡工具 ∪ `story_*` ∪ 原生七工具（受沙箱约束）。不含稿纸、上一拍修订、`conversation_mode`。

agent 子项目不注入开场白。

## 八、前端

- 桌面：稿子 60% 在中间（`StoryPane`：章目录、连续阅读、版本角标），讨论 40% 在右。只有一个输入框。写卡平台打开时稿子让位，不是真页签。
- 手机：稿子与讨论两个页签。顶栏 `agent · 稿子 N 章` 是入口（`.stage-col-head` 在窄屏上本来就是隐藏的）。
- 讨论区没有剧情气泡。写入和修订各是一张 `chapter` 通道卡片，点击定位到章。
- 数据：`hello.story` 只带章目录；正文走 `GET /api/story`（gzip）。前端按 `chapterId:version` 指纹变化才拉，纯讨论不请求。
- 流式预览：`story_append` 的参数增量 → `story_preview` → 稿子末尾「写入中」。实测 sonnet 经中转把工具 JSON 整块送达，只出一帧全量，落盘前约 6 秒可见。逐字生长取决于 provider 流不流工具参数。

## 九、这次认定的差距

用户 2026-09-22 的原话要点，不改写：

- 功能仓促，粗糙。
- 最大的区别就是正文的形态：扮演的正文就是上下文；agent 的正文与上下文分开，正文是一份可以编辑的产物。
- 要的编辑是 coding agent 那种：不一定每次都推进；文本不好就定点改，包括过往所有章，不只是最新一条；要能改到其中的每一句。
- 问的「编辑历史」是修改记录：能不能像 Claude Code 的 rewind 回到某一次输入，有没有 git 这种本地保存。会话树只能回到某一个节点。
- 归根到底：agent 模式承接了太多扮演模式的东西，它该学的是 coding agent。章节是文件的话，后端就该是一章一个文件；agent 的操作设计多个文件，不是编辑单一文件。

对照第五节和第六节：单章、唯一原文引用的 `story_edit` 做得到「改某一处」；做不到「一次变更覆盖多章、可整体看、可整体撤」。磁盘也不是一章一个文件。会话树是扮演的世界线机制，不是这份稿子的版本控制。
